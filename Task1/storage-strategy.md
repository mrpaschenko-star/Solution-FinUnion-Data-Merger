# Стратегия хранилищ

Каждый тип хранилища выбран под нагрузку и ответственность. Технологии текущих Core/CRM/процессинга неизвестны; PostgreSQL ниже — выбор для **нового аналитического слоя и Hub**, не утверждение об установленном стеке и не требование переписать АБС.

| Тип | Какие данные / роль | Выбор и обоснование | Ограничение / отказ от альтернативы |
|---|---|---|---|
| OLTP | Счета, договоры, платежи, проводки, карты/кредиты и обращения в соответствующих системах | Сохранять поддерживаемые транзакционные БД Core/Cards/Loans/CRM; ACID и локальные инварианты | Аналитические joins не направлять сюда; смена СУБД и Core — отдельные проекты |
| MDM | E01/E02/E12; согласованные E10-атрибуты | На 3 месяца PostgreSQL-backed Customer Hub: registry, crosswalk, правила/ручное stewardship. На год — управляемый MDM с matching, survivorship, workflows и audit; продукт выбрать по POC | Не мастер балансов/проводок. Собственный MVP Hub не выдаётся за полностью реализованную enterprise MDM платформу |
| DWH | Сертифицированные факты/измерения, отчётные версии, control totals | Отдельный PostgreSQL DWH на 3 месяца, dbt SQL models; целевой сертифицированный контур сохраняется, capacity проверяется | Scale-up/partitioning/read replicas не бесконечны. Миграция на MPP допустима по измеренному bottleneck, продукт не выбирается без объёмов |
| Lakehouse | Большая история карточных операций, channel events, raw/curated datasets, backfills | S3-compatible storage + Parquet + Apache Iceberg, Spark для тяжёлых преобразований, Trino для SQL | Object store сам по себе не Lakehouse; нужны catalog, atomic commits, compaction, snapshot retention, schema governance |
| Объектное хранилище | Документы, контрольные выгрузки, архивы и основания отчётов | Encrypted/versioned S3-compatible storage, checksums, legal hold/Object Lock при поддержке и требовании | Не online ledger; архив не заменяет проверяемые backup/PITR и restore DWH/MDM |
| Графовая БД | Связи parties/контрагентов/устройств для fraud/AML investigation | **Trial**, проекция минимальных связей из утверждённых data-продуктов; отдельный graph engine только при доказанной пользе traversal | Для Customer 360 и ERD графовая БД не требуется; не источник KYC-владения, доступ ограничен расследованием |
| Поиск | Поиск текста обращений, разрешённых полей клиентского профиля | **Trial** OpenSearch с row/document ACL, redaction и удалением производного индекса по policy | Для точного ID lookup достаточно индекса PostgreSQL. Не копировать весь KYC/документы ради удобства поиска |

На три месяца поставляется минимум для общей работы: Hub, Integration adapters, DWH, BI и каталог. Lakehouse начинается с ограниченного proof-of-concept, не задерживает управленческий MVP. Через год DWH отвечает за контролируемую отчётность, Lakehouse — за масштаб истории/событий; одни и те же facts не считаются дважды.

Разделение OLTP/OLAP означает отсутствие пользовательских BI-запросов к operational databases. Capture всё равно создаёт некоторую нагрузку: log-based CDC или разрешённые реплики/выгрузки ограничиваются квотами и измеряются. Нулевой overhead не обещается; если требование «аналитика не нагружает» трактуется буквально, требуется отдельная поддерживаемая реплика/экспортный контур и согласованный бюджет capture.
