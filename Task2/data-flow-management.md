# Управление потоками данных

Все значения в колонке SLA/SLO — **предлагаемые SLO**, до профилирования и согласования не договорные обязательства. Время D+1 задаётся в Europe/Moscow для отчётного дня по утверждённому банковскому календарю; региональные/операционные дни источников сопоставляются явно. Producer commit/финализация периода, durable landing и доступность потребителю измеряются отдельно.

Начальный SLO 5 минут относится к конкретному этапу; суммарная source→golden→consumer задержка может быть больше. Отдельно регистрируется сквозная freshness каждого data-продукта; время ручного review не прячется в успешный percentile автоматической обработки. Для несовместимых источников выбросы не удаляются из метрики молча.

## Общие механизмы

Контракт включает schema version, `source_system`, `legal_entity`, entity key, change/transaction ID, operation type, business/effective time, ingest time, source position и classification. JSON применяется на границе legacy ради простоты; для массовых файлов Parquet с manifest, для Kafka после POC — Avro со Schema Registry и compatibility checks. Форматы не меняются без версии adapter/consumer.

Publisher outbox/connector checkpoints, durable queues/landing и consumer inbox дают at-least-once с идемпотентным эффектом. Exactly-once между произвольной АБС, Kafka и DWH не обещается. Bounded retries с backoff+jitter, parking/quarantine и ручной replay сохраняют исходный ключ и причину. Лимиты подбираются по источнику, повтор не обходит квоту.

BI и управленческая публикация не допускают hard financial breaks; все суммы сверяются по legal entity/book/currency/business_date, а не общим итогом. Финансовые потребители получают last accepted release с явной датой, если новый не готов. Логи и метрики содержат run IDs и технические счётчики, но не PAN, ФИО или полные customer documents.
