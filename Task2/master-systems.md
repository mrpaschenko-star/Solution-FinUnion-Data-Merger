# Источники и мастер-системы

**Физический источник** хранит данные сейчас; **originator** впервые создаёт бизнес-объект; **master** утверждает эталон конкретного аспекта и распространяет его. Копия в DWH не становится финансовым мастером. `Target Core/Cards/Loans` ниже означает выбранную целевую платформу, кандидатом является соответствующая FU-система после проверки покрытия/мощности, а не уже принятое решение о готовности её заменить RB.

| Сущность | Источники As-Is / где впервые появляется | Мастер на 3 месяца | Целевой мастер / горизонт 12 месяцев | BIAN / основание |
|---|---|---|---|---|
| E01 Клиент | FU/RB CRM и клиентские записи Core/Loans; onboarding любого разрешённого канала | Customer Hub: enterprise ID и подтверждённые golden attributes; исходный KYC остаётся у ответственного банка | MDM Party с field-level authority и stewardship; CRM выполняет workflow сбора | Party Reference Data Directory; идентичность отделена от договоров/счетов |
| E02 Crosswalk | Локальные IDs возникают в каждой системе, связь создаётся Hub | Customer Hub | MDM registry, versioned merge/unmerge | Поддерживает Party boundary; не отдельный навязанный BIAN SD |
| E03 Счёт | Core соответствующего банка создаёт счёт; CRM/Loans потребляют | FU Core или RB Core по обслуживаемому счёту/книге | Target Core для переведённых счетов; RB Core остаётся мастером непереведённых до отдельного gate | Current Account для текущих счетов; финансовая целостность |
| E04 Карта | FU/RB Cards выпускает инструмент; Core даёт счёт | Соответствующий Cards | Target Cards по мигрированной когорте, RB Cards для оставшейся | Issued Device Administration — выпуск; расчёты остаются в учётном домене |
| E05 Кредит | FU/RB Loans создаёт loan facility после одобрения; Core отражает учёт | Соответствующий Loans — условия/график; Core — ledger | Target Loans по переведённым договорам, RB Loans до закрытия mapping и расчётной сверки | Consumer Loan для розницы; право собственности на долг не у MDM |
| E06 Договор | Подписывается в процессе CRM/Core/Loans; подтверждённый экземпляр в соответствующей договорной системе | Профильная Core/Loans-система по типу договора; CRM не переопределяет условия | Договорный registry с source references, authoritative terms у целевого Core/Loans | Customer Agreement — общая legal boundary, product contracts уточняются отдельно |
| E07 Транзакция | FU/RB Core journal; карточный/кредитный source fact может возникнуть раньше | Обслуживающая Core/approved accounting system | Target accounting/Core по книге/дате миграции; старые posted facts доступны как исторический регистр | Financial Accounting; событие процессинга не второй учётный факт |
| E08 Проводка | Ledger/subledger проводит запись в локальной учётной транзакции | Соответствующий Core/subledger, Finance определяет сверку | Целевой ledger для новых book entries; архив исходных записей неизменяем | Детализация E07, не MDM |
| E09 Платёж | Командный канал инициирует, payment/Core принимает к исполнению | FU/RB payment module/Core по принявшему намерение владельцу | Target payment execution по маршруту/когорте; unfinished RB операции завершаются старым владельцем | Payment Execution; ровно один исполнитель |
| E10 Продукт | FU/RB продуктовые команды, CRM/Core/Cards/Loans каталоги | Product owners утверждают mapping; Hub ведёт общий directory версий | MDM Product Directory для согласованных атрибутов; execution rules в профильных системах | Product Directory; не перезаписывать условия действующих договоров |
| E11 Обращение | Контактный центр/каналы в FU/RB CRM | CRM, принявшая case; Hub связывает клиента | Target CRM после переноса workflow/активных cases; RB CRM до безопасного перевода когорты | Customer Case Management |
| E12 Справочник | Локальные справочники систем; часть поступает из внешних утверждённых источников | Hub reference registry + назначенный бизнес-owner каждого dictionary | MDM Reference с версиями/действием и domain owners | Public Reference Data Management для общих кодов; внутренние справочники отдельно |
| E13 Согласие | Канал/CRM фиксирует действие и evidence клиента | CRM-originator/существующий consent register; Hub получает purpose projection | Единый consent registry, связанный с MDM; хранение evidence и authority выделены | Party privacy/governance; не выдумывается универсальный BIAN mapping |
| E14 Сторона договора | Договорный процесс Core/Loans и подтверждение роли | Authoritative договорная система | Целевой договорный/Core/Loans owner по когорте; Hub только identity mapping | Customer Agreement aspect; merge не выдаёт полномочия |
| E15 FXRate | Утверждённый treasury/reference feed; источник пока неизвестен | Treasury утверждает источник/тип, DWH хранит использованную версию | Тот же reference owner; MDM распространяет versioned values, DWH фиксирует snapshot | Финансовая справочная информация, отдельное подтверждение Treasury |

«По когорте» — исключительное владение, а не активная запись в две системы. Реестр хранит `(entity type, source/business key, legal entity/book, effective interval, active owner, route version)`. Изменение владельца выполняется с fencing старого writer, финальной сверкой и обработкой in-flight; аналитический cutover из Task4 **не** переносит это право.

## Правила единого клиента

1. Нормализовать форматы, сохраняя оригиналы: имя, тип лица, документы, ИНН, контакты. Номер телефона/ФИО самостоятельно не являются надёжным ключом; общий телефон семьи/организации не объединяет людей.
2. Автоматическое сопоставление допускается только на утверждённых проверенных идентификаторах и совместимых атрибутах без конфликтов. Для юрлица учитываются страна/тип регистрации/ИНН или соответствующий регистрационный идентификатор; для физлица — подтверждённые документы и дополнительные признаки. Точные правила и порог probabilistic matching устанавливаются на размеченной выборке, не придумываются.
3. Неоднозначный кандидат уходит Data Steward, высокорисковый merge — с независимым подтверждением. До решения выдаётся отдельный provisional ID; UI и аналитика показывают unresolved quality, а не гарантированное уникальное количество клиентов.
4. Survivorship по **полю**: подтверждённая KYC-версия документа от ответственного домена важнее «последней CRM-записи»; предпочтительный канал связи и актуальность контакта оцениваются отдельно. Источник, verification time, правило и согласование сохраняются.
5. Merge создаёт новую версию crosswalk/alias, прежние IDs не удаляются и не переиспользуются. Unmerge восстанавливает/создаёт отдельные customer IDs с историей mapping и affected-consumer replay. Юридические роли/финансовые документы не перезаписываются из golden profile автоматически.
6. Обратное распространение в FU/RB — identity mapping и разрешённые атрибуты с origin/version, не двунаправленное last-write-wins. Обратный echo от consumer распознаётся; конфликт source version возвращается steward, а не побеждает по часовому timestamp.

Модель не предполагает, что юридическое слияние уже произошло. Все финансовые объекты и reports сохраняют legal entity/book; внутригрупповая консолидация выполняется по утверждённым правилам Finance.
